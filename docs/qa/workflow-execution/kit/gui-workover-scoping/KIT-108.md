summary = list(
  testid      = "lipid" | "metab" | "prot" | "trx",          # <testid>-summary-* (e2e lanes, harness selectors)

## 5. Risks, and lines before and after

1. **The three copies differ in behaviour, not just in style.** The proteomics final state is the first of a preference list in the history, where lipid and metab take the head first. The record is written only for a `DIAStateAdapter` (prot) versus any `workflow_data`. Prot ignores copy failures where lipid and metab fail on three required artifacts. Prot has an export-ready gate. Each has its own integration file and writer, and prot has a four-way template resolver with a stale-template rule. The session-state payload fields differ. Each difference is a config field (§3). Unifying any of them is a parity decision that none of the user's four parity items covers (D2).
2. **The dead and drifted lipid shells.** `runLipidSummary*ObserverShell` (~260 lines) is called by no R code. It hard-codes `lipidomics_report.rmd` and omits the record bundle, so MCI-023 tests them and not the live handlers. Today's lipid summary has entry-point coverage from one `testServer` block and the e2e lane only, so KIT-101's suite is the real baseline.
3. **The selectors.** The prot module id is `session_summary`; lipid, metab and trx use `summary`. The test-id prefixes are per omic. The e2e lanes and the harness's step selectors depend on both, so the namespace and the test ids stay per omic.
4. **The `project_dirs` global.** `getProjectPaths` reads `project_dirs` from `.GlobalEnv`, so all three copies assign it before `copyToResultsSummary`. The assignment moves into the core function unchanged. Removing it would change the exported functions' contract, so it is out of scope.
5. **The `copyToResultsSummary` branch move** must give an identical file set per omic. Notebooks call it, so its signature is frozen. Q-07 is already quarantined on its backup count.
6. **The proteomics integration object (observation, not verified, no change proposed).** On a non-native session, `completeProtSummaryWorkflowArgsSave` calls `saveRDS` on what `resolveProtSummaryFinalS4State` returns, which is `getDIAStateReference(...)`: a state reference, not the object. KIT-101's baseline should record the file's class before anyone relies on it.
7. **The trx export step.** The managed path dispatches three products: the export and two figures. The in-process path runs the reference runner and the publications. The generic runner must keep `acceptTrxRuviiiExport` on the head, the record's `trx_ruviii_export` outcomes and the DA head unchanged (MCI-032 checks all three).
8. **Ordering with KIT-109.** KIT-109 removes the profile hooks and the duplicate copies. If KIT-108 rewires every omic and leaves the old files unreferenced, their seam tests still pass against dead code for one ticket. That is harmless, but it is reported.

## Decisions needed (for KIT-101's design or the user)

- **D1:** proteomics on the shared module. Recommended yes: the same layout and flow, with its resolver, native integration and final-state rule as config.
- **D2:** keep the copies' behavioural differences as per-omic config (recommended; no science change) or unify them (each would need a failing-first test and the user's decision).
- **D3:** report rendering and the proteomics integration write stay in process inside core functions. Worker dispatch would be a new mechanism and is out of scope.
- **D4:** whether the old summary files are deleted in KIT-108 or in KIT-109. The plan says KIT-109.
