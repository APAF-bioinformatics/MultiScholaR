# KIT-101 scoping note: GUI workover design and boundary baseline (2026-11-06)

**Scope.** Read-only scoping at `c4839d25` on `performance-v2`, done with grep, wc and reading. No R, test or check runs were made, because other jobs were using the machine. The ticket's summary is the section "Scoping (2026-11-06)" in `tickets/kit/KIT-101.md`.

**What this note covers:** the four scoping questions, the evidence, the proposed boundaries, and the decisions the user needs to make before KIT-101 is authored in full.

**Authority:** the series goal (user, 2026-11-06), quoted in the ticket.

**How the line counts were made.** `wc -l` per file. The reactive versus non-reactive split comes from a token classifier, written in awk in the session scratchpad and not committed:
- It splits every top-level `name <- function(` definition up to the next top-level assignment.
- A function is **reactive/UI** if its body contains any of `shiny::`, `input$`, `output$`, `session$`, `observeEvent`, `reactive`, `render*`, `showNotification`, `update*Input`, `tags$`, `NS(`/`ns(`, `moduleServer`, `withProgress` or `req(`. Otherwise it is **non-reactive**.
- A non-reactive function counts as **data-manipulating** if it uses dplyr/tidyr/purrr verbs, joins, pivots, `*apply`, readers or writers, `stats::`, `log2`, `median` or `quantile`.
- These are heuristic upper and lower bounds, not exact counts. Lines outside functions (roxygen and file headers) are excluded from the split.

## 1. Proteomics as the pattern

### Verdict

**Partly.** The user's belief holds for two parts: proteomics' QC sub-tabs and its DA run handler are the light observer layer, and they are the template to extend. It does not hold for proteomics' GUI as a whole:
- The proteomics GUI is the largest of the four omics.
- It is not lighter per line than lipid or metab.
- Its normalisation, enrichment, design and import tabs still carry backend work, dead test seams and code that the core calls back into.
- Its normalisation, enrichment and DA kernel run in the GUI R process. Lipid, metab and trx run the equivalent steps on the worker.
- Proteomics sits on its own DIA core, not on the omics declaration binding that lipid, metab and trx share.

### Separate core

Proteomics runs on the DIA core:
- `R/utils_workflow_dia_*.R`: 6 files, 9,198 lines;
- `R/utils_workflow_prot_declarations.R`: 1,294 lines.

`omicsDeclarationBindings()` (`R/utils_workflow_omics_declarations.R:588-591`) lists only lipid, metab and trx. A proteomics declaration binding does not exist.

### Proposed boundary

- **Build on what three omics already share.** The shared GUI layer is built on the omics binding and its runner (`installWorkflowOmicsActions` and `workflowOmicsManagedActions`), which lipid, metab and trx already use.
- **Adopt proteomics' two good patterns:**
  - the QC spec table: one sub-tab is a UI plus one core operation;
  - the DA handler shape: one run click calls one core runner, the publication is a managed step, and display renders on demand.
- **Proteomics joins through a DIA binding adaptor.** The adaptor maps the shared components' runner calls onto the `runDIAReference*` runners and the managed steps. It is new code and needs a scope decision (decision a).
- **What stays separate, and why:**
  - **Proteomics' peptide and protein QC sub-tab servers.** These are DIA-specific steps that vary by route: DIA (7 peptide and 5 protein sub-tabs) and DIA_LIMPA (4 peptide and 3 protein sub-tabs), 17 sub-tab servers in all, with TMT and LFQ to come. They are not shared with any other omic. They plug into the shared QC shell as configured sub-tabs, already in spec-table form.
  - **Enrichment.** It becomes its own omic-agnostic module, with proteomics the only consumer for now (user, 2026-11-06).

## 2. The omic configuration contract

### Raw material

**The trx profile has 65 fields:** 34 in `trxOmicProfile()` and 31 in `trxNormDaSummaryProfile()` (`R/mod_transcriptomics.R:32-73`). The lipid modules read 60 distinct `profile$` fields across 18 files. The metab modules read none, and trx uses only the lipid modules. The 65 fields fall into three groups:

| Group | Count | Fields |
|---|---:|---|
| Declarative | 34 | labels, ids, keys, columns, help text: `omic_type`, `prefix`, `testid`, `label`, `label_lower`, `class`, `workflow_type`, `data_format`, `import_title`, `formats`, `assay_name`, `id_label`, `annotation_label`, `import_help`, `design_help`, `state_name`, `state_description`, `qc_title`, `binding`, `report_template`, `report_dir`, `norm_tabs`, `norm_stage_labels`, `norm_ruv_heading`, `norm_ruv_help`, `da_threshold_label`, `da_lfc_label`, `long_table`, `da_columns`, `da_volcano_interactive`, `summary_placeholder`, `summary_description`, `integration_filename`, `integration_missing_message` |
| Core adaptors | 20 | functions that read, validate, build, run or write: `load_preview`, `process_import`, `run_order`, `group_levels`, `validate_design`, `build_object`, `record_provenance`, `read_metadata`, `read_state`, `finalize`, `da_formula`, `da_contrasts`, `da_export`, `da_run_reference`, `da_with_source`, `integration_write`, `integration_ready`, `summary_state_object`, `summary_context`, `ruviii_m_choices` |
| Server or UI substitutions | 11 | `qc_tabs`, `qc_init`, `register_qc_summary`, `norm_options`, `norm_server`, `da_server`, `da_model_ui`, `da_static_volcano`, `da_widget`, `summary_export_ui`, `summary_server` |

**The principle ("no backend in the frontend"):**
- The configuration holds data and *references* to core functions.
- The core adaptors live behind the binding, not in GUI files.
- Server substitutions become ids chosen from the shared component library. Swapping a whole server through a hook is what made the interim GUI "lazy and incomplete" (user, KIT-097).

### Proposed fields, per omic: `omicGuiConfig(<omic>)`, a plain list

**Identity and shell**
- `omic_type`, `prefix`, `testid`, `label`, `label_lower`.
- `routes`: the workflow types.
  - proteomics: `DIA`, `DIA_LIMPA`, and the TMT and LFQ routes the import offers;
  - lipid: `LIPIDOMICS`;
  - metab: `METABOLOMICS`;
  - trx: `TRANSCRIPTOMICS`.
- `tabs`: ordered `{status_key, tab_value, module_id, title, icon, testid}`. These are kept per omic because the e2e lanes and the KIT-098 driver depend on them:
  - proteomics: tabset `workflow_tabs`; values `setup/design/qc/normalization/da/enrichment/session_summary`; module ids `setup_import/design_matrix/quality_control/normalization/differential_expression/enrichment_analysis/session_summary`; test ids `prot-tab-*` (`R/mod_proteomics.R:44-198`);
  - lipid, metab and trx: tabset `<omic>_tabs`; values and module ids `import/design/qc/norm/de/summary`; test ids `<prefix>-tab-*`.
- `status_keys`: derived from `tabs`, and the chain that opens the next tab comes from the tab order.
  - DA key: proteomics uses `differential_expression`; the others use `differential_analysis`.
  - Proteomics adds `enrichment_analysis`.
- `bus_fields`: the omic's extra `workflow_data` fields. Proteomics, for example, adds `fasta_file_path`, `taxon_id`, `organism_name` and `uniprot_dat_cln` (`R/mod_proteomics.R:205-245`).

**Binding (core side; the GUI never computes)**
- `binding`: the declaration binding. Proteomics needs a DIA adaptor (decision a).
- `runner`: `omics_actions` or `dia_managed_step`, or one kind after the adaptor exists.
- `class`, `state_name`, `state_description`, `read_state`, `read_metadata`.

**Import**
- `formats`: vendor formats, kept per omic (user decision).
  - proteomics: diann, spectronaut, fragpipe, maxquant, pd_tmt (`R/mod_prot_import_ui.R:55-61`), and the DIA route choice (`:66-68`);
  - metab: msdial, progenesis, xcms, compound_discoverer, custom (`R/mod_metab_import_ui.R:36-42`);
  - lipid: msdial, lipidsearch, custom (`R/mod_lipid_import_ui_helpers.R:78-83`);
  - trx: trx_counts.
- `aux_inputs`:
  - proteomics: FASTA, organism and taxon, optional mapping files;
  - lipid and metab: second assay, internal-standard pattern, sanitisation;
  - trx: none.
- `import_title`, `import_help`, `id_label`, `annotation_label`, `assay_names`.
- Core: `load_preview`, `process_import`, `validate_import`.
- Text-numeric sample columns are converted for every omic (parity decision).

**Design**
- `design_help`, `formula_default` (`"~ 0 + group"`).
- Core: `run_order`, `group_levels`, `validate_design`, `build_object`, `record_provenance`.
- `annotation_step`: proteomics only. The UniProt fetch and FASTA processing move into the core as a step.

**QC**
- `qc_title`.
- `qc_groups`: a list of groups. Proteomics has two (peptide, protein); the others have one. Each group is a list of sub-tab specs `{id, title, ui, operation, routes, needs_paths}` in the shape of `getProtQc*ModuleSpecs`.
  - lipid and metab: intensity, duplicates, ITSD, finalise;
  - trx: expression filter, finalise.
- `qc_finalize`: the QC-finalise design-alignment check runs for every omic (parity decision).
- `filtering_metrics`: from the binding.

**Normalisation**
- `norm_panels`: ordered ids from one shared panel library, each with per-omic options:
  - `itsd`;
  - `log2`;
  - `between_sample` (methods);
  - `ruv` (modes automatic/manual/skip, heading, help);
  - `correlation_filter`;
  - `tmm_logcpm`;
  - `ruv_grid`.
- Which panels each omic uses:
  - proteomics: between_sample, ruv, correlation_filter; the DIA_LIMPA route passes through;
  - lipid and metab: itsd, log2, between_sample, ruv, correlation_filter;
  - trx: tmm_logcpm, ruv_grid with RUVs.
- `norm_plot_tabs` (for example pca, rle, density, correlation, ruv, log), `norm_stage_labels`, `norm_export` (the filtered-session export).

**DA**
- `da_model`: `limma` (proteomics), `limma_per_assay` (lipid and metab), `edgeR_QL` (trx), plus the fixed settings from `binding$da_fixed`.
- `da_inputs`: formula; threshold label and default (q-value, or "FDR (BH)"); lfc label, and whether it is a TREAT test or display only (trx).
- `da_columns`: `{id, label, logfc, pvalue, significance, significance_label}`.
- `long_table`: `da_proteins_long`, `da_lipids_long`, the metab table, `da_genes_long`.
- `da_views`:
  - static volcano;
  - interactive volcano, on demand (KIT-097);
  - heatmap with tree cut (the metab tree-cut defect is fixed, parity decision);
  - table;
  - assay selector (lipid and metab).

**Enrichment** (`NULL` except for proteomics, for now)
- `identifier_column` and identifier type: UniProt accession today.
- `gene_name_source`.
- `background`: `per_contrast_da_table`, as the declaration states (`R/utils_workflow_dia_da.R:545`).
- `annotation_source`: `uniprot_dat_cln` / GO annotations.
- `services`: gprofiler2, clusterProfiler.
- `taxon` and `organism_filter`.
- cutoffs: `up`, `down`, `q`; `correction_method`; `exclude_iea`.
- These match the declaration's parameters (`R/utils_workflow_dia_da.R:543-544`).

**Summary, report and export**
- `report_templates` per route:
  - proteomics: `DIANN_report.rmd`, `DIANN_limpa_report.rmd`, `TMT_report.rmd`, `LFQ_report.rmd`;
  - `lipidomics_report.rmd`, `metabolomics_report.rmd`, `transcriptomics_report.rmd`.
- `report_dir`, `summary_placeholder`, `summary_description`.
- `export_steps`: ordered `{id, ui_panel, operation, ready, filename}`. The publication copy is common to all omics; trx's RUVIII integration export is one step.

## 3. The entry-point behaviour suite

### Driver

`shiny::testServer` on each omic's public top-level server:
- `mod_proteomics_server`;
- `mod_lipidomics_server`;
- `mod_metabolomics_server`;
- `mod_transcriptomics_server`.

It is driven through namespaced inputs (`session$setInputs`, for example `de-run_da_analysis`), with no mocks of internals. Under `testServer` there is no managed application, so the steps run in process through the same core wrappers. The managed path stays proven by the e2e browser lanes (shinytest2 `AppDriver`, `tests/testthat/helper-e2e-browser.R`).

shinytest2 is too heavy to serve as the per-ticket suite. It stays the lane-level proof.

### What is captured

Captures are taken after every step and frozen on today's code:
1. the committed state name and state history (`workflow_data$state_manager`), and `tab_status`;
2. a digest of each committed state's content, read through the core readers (`read_state` / `readWorkflowOmicsState`, and `readDIAStateMetadata` for proteomics), so the digest is stable across the move;
3. outputs:
   - the set of output names;
   - text output values;
   - plot identity and alt text, not pixels;
   - DT and table data digests;
   - the contrast choices;
4. artifacts: paths under the experiment directories and the sha256 of the deterministic files (`.tsv`), under the volatile-field policy of `tests/testthat/helper-module-ci-oracles.R`;
5. at least one refusal per tab, with its notification text and status. Examples: DA with no loaded session; an invalid import.

### Corpora

- Lipid, metab and trx use the KIT-040 `*_screen` recipes (`tools/profiling/kit_omics_corpus.R`). That generator exists only in the source tree, and today's journeys `skip_if_not` it exists. The entry suite must either commit small fixtures or treat a skip as a failure, as KIT-097's lane does.
- Proteomics uses `tests/testdata/e2e/prot_dia`, plus:
  - the enrichment doubles (`helper-e2e-enrichment-doubles.R`);
  - an offline UniProt cache, because the design save fetches UniProt over the network.
- A DIA_LIMPA journey is optional and needs a decision.
