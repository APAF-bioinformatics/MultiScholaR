## 3. The shared component boundary and the config fields

Boundary: one `mod_omics_da_ui(id, config)` / `mod_omics_da_server(id, workflow_data, experiment_paths, config)` built from
lipid's module (it already carries trx through `profile`). The exported `mod_lipid_da_*`, `mod_metab_da_*` (and, if
adopted, `mod_prot_da_*`) stay as thin wrappers with their signatures. The module holds rows and selectors, renders,

## 4. How close proteomics is, and whether it can share the module

Close in the UI: the same three tabs and sidebar, 35 of 39 ids, the same heatmap controls including tree cut.
Different underneath:

- results are a store manifest (`dia.da_results.v1`), not rows: the table pages from the store, the heatmap is a
  saved clustering product, the interactive volcano is the DA-time page asset;
- the DA kernel runs in the app process under a managed session too (`runDIAReferenceDaAnalysis`, KIT-019: only the
  publication runs in the worker, through `installWorkflowManagedStep`, a different managed mechanism from the omics
  runner);
- it auto-loads the head on tab selection and `state_update_trigger` and clears results when the population changes
  (`invalidateDIAVisibleResults`);
- it commits `da_ui_params` on the state; enrichment (KIT-107) and the summary (KIT-108) read the manifest
  (`workflow$da_analysis_results_list`) and these parameters;
- status keys `differential_expression` and `differential_abundance`, and `enrichment_analysis` reset to pending.

Verdict: proteomics can share the UI and the render registrations (status, contrasts, volcano, heatmap, table,
Save Heatmap) through config readers for the manifest. Its run, session load and init handlers stay proteomics
adaptors. Putting its kernel on the worker (or on `runWorkflowOmicsManagedDa`) is a backend change that alters the
managed flow and the enrichment hand-off; it does not "fit" this ticket and needs the user's decision.

## 6. Risks, and lines before and after

Risks:

- Small lipid/metab differences the entry-point suite will see: metab's table filter treats `Combined` as all
  assays and keeps `drop = FALSE`; metab checks session assay names; text strings; selector defaults. Each is a config
  value or kept identical.
- The on-demand default changes lipid, metab and proteomics behaviour (checkbox `TRUE` today). This is a visible
  change: it needs the user's confirmation as a parity decision.
- The in-process page is as large as the widget it replaces (the data travels inline). Whether it avoids KIT-097's
  hang must be measured in a browser, not assumed.
- Proteomics: kernel in the app process (above); the enrichment and summary hand-offs read its manifest unchanged.
- Hard-coded omic: `handleLipidDaRunAnalysisPreflight` asks `workflowOmicsManagedActions("lipidomics")` for every omic;
  trx skips it only because the class check fails. The shared module must use the config's omic.
- Heatmap clustering stays in the app process for lipid, metab and proteomics (not moved here).
- Metab's saved heatmap parameters change from NULL tree-cut values to `none`/4/10/5 (part of the tree-cut fix).
- Unrelated discoveries, left untouched: prot UI defines `heatmap_show_dendro`, which no server reads; prot server
  reads `volcano_show_labels` and `volcano_label_top_n`, which the UI never defines (defaults apply).
