**Shape.** Lipid and metab are one design written twice: the same four sub-tabs (Intensity Filter, Duplicate Resolution, Internal Standards, Finalize QC), the same input and output ids, the same core declarations (`omicsIntensityFilterStep`, `omicsDuplicateResolutionStep`, `<prefix>_qc_finalize`, `<prefix>_filtering_metrics`), the same managed/in-process branch. The ITSD metric kernels are identical apart from their names and one argument name (`getLipidInternalStandardMetrics(lipid_id_col=)` vs `getInternalStandardMetrics(metabolite_id_col=)`), as are `getLipidQuantData`/`getMetaboliteQuantData` and `validateLipidDesignAlignment`/`validateMetabDesignAlignment` (only the non-sample patterns and the mapping key differ). Text differs by the feature noun only.

Real behaviour differences between lipid and metab (all in finalise):
1. Lipid's finalise runs `validateLipidDesignAlignment`; metab's checks only non-empty assays and design (the parity decision).
2. Lipid refuses a finalise when any assay has zero rows; metab only when there are no assays. Not covered by the parity decision (see decision D2).
3. Lipid's `completeLipidQcS4TabStatus` also moves `normalization` from `disabled`/`locked` to `pending`; metab's sets only `quality_control`. All three app shells (lipid, metab, trx) have their own observer that moves `normalization` from `disabled` to `pending`, so the app-level end state is the same; a module-level capture differs (decision D3).

Smaller differences with no visible effect: duplicate-resolution products (lipid's value is `counts$before/after`, metab's is `stats` per assay; both render the same text), `history[[n-1]]` vs `history[n-1]` in revert, notification ids prefixed per omic.

Proteomics is a different shape: two groups (Peptide QC, Protein QC) whose sub-tab lists depend on the workflow type, each sub-tab a full module with its own managed step (`installWorkflowManagedStep`), and no finalise tab. Its spec lists (`list(id, title, uiFn, serverFn, needsExperimentPaths)`) are already the registry pattern this ticket needs; the shell around them is not reusable (string `exists()/get()` lookup, debug messages, duplicated branches).

## 3. The shared shell boundary

### 3.1 Shell (`R/mod_omics_qc.R`, new, estimate about 150 lines)

`mod_omics_qc_ui(id, config)` and `mod_omics_qc_server(id, workflow_data, experiment_paths, omic_type, experiment_label, qc_trigger, config)`. It does only what the three shells do today:
- render the tabset (id `<prefix>_qc_tabs`, as today) when `config$qc_ready(workflow_data)` is true, else the "complete the Design Matrix step" alert;
- start the sub-tab servers once, on `qc_trigger()` or, when `config$qc_auto_init` is true, when the state's class is `binding$class`;
- for proteomics, nested groups and the completion observer (see 3.3).

### 3.2 The sub-tab plugin interface

A tab spec, modelled on proteomics' existing spec lists but with function references instead of names:

```r
list(id = "intensity", title = "Intensity Filter",
     ui = function(id, config) ...,                    # returns a tabPanel
     server = function(id, context) ...)               # context: workflow_data, experiment_paths, omic_type, experiment_label, config
```

A group spec (`list(id, title, tabs)`) renders a nested tabset under `ns(id)` and starts its tabs inside `moduleServer(id)`, so proteomics' ids (`quality_control-protein_qc-intensity_filter-...`) are unchanged. Sub-tab ids are frozen at today's values: `intensity`, `duplicates`, `itsd`, `s4_finalize`, `filter`, and proteomics' `peptide_qc`/`protein_qc` and spec ids. The journeys (`tools/profiling/workflow_kit.R:24-48`), the residency helper and the e2e lanes address these ids.

## 6. Risks, decisions needed, and lines before and after

**Risks**
1. **Ids.** Any change to sub-tab or group ids breaks journeys, e2e and the residency helper. Freeze them (identity guard).
2. **Silent skips.** See section 5.
3. **Duplicate product shapes.** Lipid and metab products differ; normalise in the reader, never in the kernel (the record and the oracles depend on it).
4. **In-process metrics.** The shared action computes `binding$filtering_metrics` where the module now passes the object. The figures are built from the same function, but the filtering-progress accumulation (`getFilteringProgressLipidomics`) must be called in the same order. The journeys and the entry-point suite prove this; inspection does not.
5. **Trx alignment.** It needs `readWorkflowOmicsShell` on a trx state, which no trx code calls today (it reads metadata only). The zero-row prototype must keep the column names and `args$group_levels`. This is untested.
6. **Metab alignment validator.** `validateMetabDesignAlignment` lives in `mod_metab_design_validation.R`, and KIT-103 may move or merge the design validators. KIT-104 consumes what KIT-103 leaves.
7. **Public API.** 20 QC module functions are exported (`mod_lipid_qc_{ui,intensity,duplicates,itsd,s4}_{ui,server}`, `initializeLipidQcSubmodules`, `mod_metab_qc_*`). They stay as thin wrappers over the shared modules, about 70 lines (estimate). `mod_lipid_qc_server` is not exported, but trx calls it.
8. **Proteomics.** Moving its orchestrator touches three e2e lanes and four routes for about 410 lines of saving. Its sub-tabs use a different managed mechanism and different algorithms, and stay as they are.
9. **ITSD has no committed state.** No journey covers it, so the entry-point suite must drive `analyze_is` for lipid and metab.
10. **Convention divergences kept** (existing-code scope rule): `renderUI`-generated output ids (`dup_table_<assay>`), `wellPanel`/`fluidRow`, and the managed runner in place of `ExtendedTask`.
11. **Harness.** The step map labels modules by name (`module("qc_intensity")`, `module("lipid_qc") (trxOmicProfile)`). These are label strings only, but under frozen protocol v1.8 they should not be edited without the user. `tools/profiling/workflow_kit.R` and its test changed during this pass in KIT-098's commit `c783e97a`. No `R/` file changed between `c4839d25` and `c783e97a`, and the step-map lines cited here are the same at both.

**Decisions needed (from the user, via KIT-101)**
- **D1.** Should the proteomics QC orchestrator move onto the shell (spec lists kept, sub-tabs untouched)? Recommended: yes, the orchestrator only. If KIT-101 keeps proteomics separate, the shell serves lipid, metab and trx, and proteomics keeps its 523 lines.
- **D2.** Lipid refuses zero-row assays at finalise; metab and trx do not. The parity decision covers alignment only. Recommended: keep per omic unless the user extends parity. If extended, add a test that fails before for metab.
- **D3.** Normalisation hand-off in finalise. Recommended: lipid's behaviour for all omics; the app-level end state is unchanged. The entry-point suite must then record the metab module-level difference (normalisation `pending` where it was `disabled`), or the hand-off stays as each omic does it today.
- **D4.** Delete the lipid/metab copies here, or in KIT-109 as the plan says? Recommended: KIT-109. KIT-104 rewires the entry points and moves the computation; the dead copies keep their seam tests green until one quarantine in KIT-109. KIT-104 quarantines only the profile-hook tests it replaces (MCI-028.4, the trx finalise case).
- **D5.** Should the step-map module labels in the frozen harness change? Recommended: no, because they are labels.
