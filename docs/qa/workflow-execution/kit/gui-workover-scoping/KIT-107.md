## 2. Classification: what is GUI and what moves to the core

### Is enrichment computation already in the core?

**Only the kernel call is.** On the application path, DA always publishes a `dia.da_results.v1` manifest (`utils_workflow_dia_da.R:449`; session load at `mod_prot_da_handlers_load_session.R:296`). So the module runs the declaration through `runDIAReferenceEnrichment`.

Everything around that call is computed inside the module:

- the parameter validation and backend routing;
- the DA-table read (`createDAResultsForEnrichment` reads `da_proteins_<contrast>_long_annot.tsv` from `da_output_dir`);
- UniProt annotation loading or download;
- annotation matching;
- the mixed-species organism filter;
- directory creation;
- per-contrast result reshaping (including g:Profiler column aliasing);
- display-table saves;
- the `enrichment_completed` state save;
- restore after Open.

The non-manifest branch is reachable only from tests. It covers `executeProtEnrichProcessEnrichments`, the `theObject` and global-environment fallbacks, and the legacy valid-state list in `registerProtEnrichSelectedTabObserver`.

### Stays in the GUI layer (reactive or display), about 2,800 lines

- `mod_prot_enrich_ui` and `mod_prot_enrich_server`.
- The 29 `setupProtEnrich*` wrappers (a candidate for collapse, see §6).
- The 22 `registerProtEnrich*` observers and outputs. The legacy body of the tab-selected observer goes if the non-manifest branch is removed.
- The 15 `format*`/`render*` functions and the download zip.
- The run shell, finalise, notify and log functions, plus `createProtEnrich*Reactive*`.
- Contrast-choice display helpers: `buildProtEnrichContrastChoices`, `resolveProtEnrichRawContrastName`, `resolveProtEnrichSelectedContrastResults`, `resolveProtEnrichContrastsTable`.
- Tab-status and progress functions.

### Proposed core surface (smallest sufficient)

Two functions, beside the existing declaration:

- **`runWorkflowEnrichment(workflow, config, manifest, parameters, process_fn)`.** It validates, routes the backend, assembles inputs through the configuration's hooks, runs the declaration, reshapes per contrast, saves display tables and the `enrichment_completed` state, and returns values.
- **`restoreWorkflowEnrichment(manager, config)`.**

The GUI writes the returned values to the bus: `enrichment_analysis_results`, `enrichment_ui_params`, `enrichment_organism_filter` and `tab_status`.

The declaration's `input_class` and `omic_type` come from the configuration. For proteomics the name, `product_type` and schema stay exactly as they are, so saved identities and replays do not move.

The run stays `in_process`, as today, because of the network call and the test-mode double inside the app process. Moving it to the worker is a separate decision; see risk R6.

**Limits of "configuration only":**

- **Transcriptomics.** It holds for gene and protein identifiers on organisms g:Profiler supports. The clusterProfiler fallback also needs an annotation table of the UniProt-GO shape, which transcriptomics has no source for today.
- **Lipidomics and metabolomics.** g:Profiler GO and the clusterProfiler GO fallback do not apply. Their enrichment is a different kind: KEGG or Reactome compound ORA through ChEBI mapping, LION lipid ontology, or lipid-class ORA. Each needs a new backend kernel and an annotation mapping. The configuration can name the kind and the shared GUI can host it, but **a kernel per kind is new code, outside this series**.
- **The existing multi-omics helpers do not cover this.** `runKeggEnrichment` and `runReactomeEnrichment` take MOFA ranked weights, not DA tables, so they are not drop-in.

## 4. The shared component boundary

**The shared GUI module** (`mod_omic_enrich_ui/server(id, profile, workflow_data, experiment_paths, selected_tab)`) is reactive only. It covers:

- the settings panel, built from configuration labels; the organism-filter panel is shown only when `organism_filter` is set;
- the method display and the run button, which makes one core call inside `withProgress`;
- status and notifications;
- result tables paged from store references, plots and the zip download;
- contrast choices when the DA results arrive;
- the taxon and mixed-species prefill;
- restore on Open, which calls the core.

The STRING-DB tab stays as it is for proteomics, behind a configuration flag.

`mod_prot_enrich_ui` and `mod_prot_enrich_server` stay exported as thin wrappers with the proteomics profile. Every input id, output id, testid and status string stays the same, because the e2e lanes address `e2e_input_id("proteomics", "enrich", ...)`.

**The core** owns two entry points (`runWorkflowEnrichment`, `restoreWorkflowEnrichment`), the existing declaration (generalised by configuration) and the per-omic hooks named in the configuration. The proteomics hooks are the existing UniProt, organism-filter and DA-table-read functions, moved out of the module.

**The kernels** (`processEnrichments`, `perform_enrichment`, `createDAResultsForEnrichment`, `createEnrichmentResults`) stay unchanged and exported.

**Boundaries with neighbouring tickets:**

- **KIT-106** owns the DA manifest and `da_columns`/`long_table`; KIT-107 only reads them.
- **KIT-101** owns the field names.
- **KIT-063** owns the multi-omics helpers.
- **KIT-083 and KIT-066** own real-data enrichment proof.

## 6. Risks, and lines before and after

**Risks:**

- **R1. Silent skips.** prot-11a's binding guard and its source-by-path loader turn helper renames into skips. The skip count must be compared with KIT-101's baseline, and every affected test must be listed in the quarantine manifest with the internal that replaced it.
- **R2. The legacy non-manifest branch.** It is unreachable from the app but exercised by seam tests. Removing it is a decision, under the quarantine rule. Keeping it means carrying it through the move.
- **R3. Hard-coded kernel columns.** The kernel hard-codes `fdr_qvalue`, `log2FC`, `Entry` and `go_id_go_*`. Generalising means a column rename in the core adapter, which is the identity for proteomics. For other omics the path stays untested until it is switched on. Do not claim it works for trx without a test; no other omic is switched on here.
- **R4. Saved identities.** The product identity includes the declaration name `enrichment`, its parameters and the service. Renaming the declaration, the product type or the schema for proteomics would change identities and replays, so the names must be kept.
- **R5. The DA file contract.** `createDAResultsForEnrichment` silently returns NULL tables (a warning only) if the DA TSV name `da_proteins_<contrast>_long_annot.tsv` changes. KIT-106 must not rename it for proteomics, and the entry-point suite must catch an empty input.
- **R6. In-process execution.** The run stays in the Shiny process (declaration `in_process`, dispatch refused; network call; test-mode double in the app). Moving it to the worker is a behaviour and performance change outside this ticket unless KIT-101 decides otherwise.
- **R7. Whole objects in the reactive layer.** The module holds whole objects in `reactiveValues` (`enrichment_results_full` with plotly objects, `current_s4_object`), contrary to KIT-075's references-only rule. Changing that is a memory change not required here. Recorded, not done.
- **R8. Duplicated organism table.** The supported-organism table is duplicated in the module and the kernel. The configuration should take the module copy; the kernel copy stays because the kernel is unchanged. Drift would desynchronise the displayed method from the one actually run.
- **R9. Exported API.** `mod_prot_enrich_ui`, `mod_prot_enrich_server`, `processEnrichments`, `perform_enrichment`, `createDAResultsForEnrichment`, `createEnrichmentResults` and `getEnrichment*` are exported and must stay.
- **R10. Placeholders and no-ops.** The STRING-DB placeholder and the `updateProtEnrichStateManagerUiParams` no-op are kept as they are; removing either is a decision, not part of this ticket's outcome.
