## One mechanism: three declarations on the owner, plus the one storage mechanism they need

- **Declarations** (`R/utils_workflow_prot_declarations.R`, registered in `R/utils_workflow_operations.R` with defaults maps, labels and `fixed`): `peptide_log2_matrix` (unit row; kernels `calcPeptideMatrix` then `log2TransformPeptideMatrix`; no parameters; `fixed = list(nonpositive_to_na = TRUE)`; label `4_log2_matrix`; state `log2_matrix`), `peptide_accession_cleanup` (unit feature group by the protein group; the peptide `chooseBestProteinAccession`; parameters `delimiter` → `[chooseBestProteinAccession] delim`, `aggregation_method`, `seqinr_accession_column` → `[chooseBestProteinAccession] seqinr_accession_column`, `fasta_sha256` as KIT-026 declares it; label `7_annotation_cleanup`; state `peptide_accession_cleaned`), `protein_dpc_quant` (unit whole matrix; the peptide method of `proteinMissingValueImputationLimpa`; parameters `engine`, `dpc_slope`, `chunk` → `[limpaDpcQuant]`; label `9_protein_dpc_quant`; state `protein_dpc_quant`; its `config` carries the realised DPC intercept and slope, the interpretation band, proteins quantified, peptides used, missing percentages, the engine and its version and the limpa version, lifted into the record's `outcomes`). The two peptide steps finish through `finishDIAReferencePeptideStep` (new hand-off branches), the DPC step through `finishDIAReferenceProteinStep`; each has a worker handler and validator (`computeWorkflowPeptideLog2Action`, `computeWorkflowPeptideAccessionAction`, `computeWorkflowProteinDpcQuantAction`) and an in-process entry point (`runDIAReferencePeptideLog2Matrix`, `runDIAReferencePeptideAccessionCleanup`, `runDIAReferenceProteinDpcQuant`). `publishDIAProteinTables` publishes the DPC step's limpa QC figures (`generateLimpaQCPlots` on the hydrated state) into `protein_qc`.
- **Section map by route** (B-23): `workflowSectionOperationsByType$DIA_LIMPA` names the route's declarations for `log2TransformPeptideMatrix`, `chooseBestProteinAccession` and `limpaDpcQuant`; `workflowOperationForSection(section, workflow_type)` consults it first; `setDIAStepProvenanceForSection` passes the owner's type; the analysis record's reverse map reads `workflowAllSectionOperations()`.
- **Owned args entries** (the storage mechanism): the class declaration gains `args_as_owned` (`ProteinQuantitativeData`: `limpa_dpc_quant_results`). `checkpointDIAExecutionResult` saves each present entry as one owned value (`saveDIAStateValue`, codec rds, label `owned_args:<entry>`), keeps the reference in `slots$args` and roots it in the checkpoint's `dependencies`; a re-checkpoint of a hydrated object whose entry is unchanged (content digest against the source state's saved value) reuses the reference, so the shared protein steps after the quantification write it once; `rebuildDIACheckpointObject` reattaches the value whenever the assay is hydrated (a projected read keeps the reference), so every reader of `@args$limpa_dpc_quant_results` works unchanged. A state that never carried the entry (every DIA route state) checkpoints exactly as before.
- **Engine dispatch**: the generic and the peptide method gain `engine`; `resolveLimpaDpcEngine` (`limpa` by default, `fastlimpadpc` honoured when installed, `workflow_engine_unavailable` otherwise, `workflow_engine_invalid` for any other value); the method's two engine calls (`dpc`, `dpcQuant`) are resolved by name; the results list records `engine` and `engine_version`. - **Modules**: `R/mod_prot_qc_peptide_log2.R`, `R/mod_prot_qc_peptide_accession.R`, `R/mod_prot_qc_protein_dpc_quant.R` on the managed-step pattern (`installWorkflowManagedStep`, the in-process observer, Revert), replacing KIT-046's placeholders; the DPC tab offers the installed engines, limpa first.
- **Software block**: `workflowSoftwareIdentity` adds namespaces loaded after its first call (the engine a later step loads) and `diaStepProvenanceEntry` extends the build's package list, so the record names `limpa` and `fastlimpadpc` with their versions.
- **Reproduced defect repaired in the kernel**: limpa 1.4.0 and 1.4.2 return `dpcQuant`'s `genes` without a `protein.id` column (NPrec, PropObs only), so the peptide method set no row names and the protein object carried row numbers as its ids (on the kit host every protein was then dropped by `filterMinNumPeptidesPerProtein`). The ids are now taken from `genes$protein.id` when present (fastlimpadpc) and from the row names of `E` otherwise; the quantities are unchanged. The retired in-memory limpa route had the same defect on the user's limpa 1.4.0.

## Deviations and claim limits

- **Default engine `limpa`, not `fastlimpadpc`**: the ticket's own consequence of the determinism result, applied under the afk authorisation and recorded in the plan's decision record for the user's review; the user may pin `RAYON_NUM_THREADS=1` for the worker (deterministic on this host) and overrule.
- **Step-map units recorded without the user's confirmation row** (the user is afk): `peptide_log2` row, `peptide_accession` feature group, `dpc_quant` whole matrix, with `flag: null` and a note; confirmation requested in the decision record.
- `seqinr_accession_column` defaults to the shipped `uniprot_acc` (the GUI's FASTA table carries `database_id`, renamed to the declared column as the protein cleanup does); the script's `cleaned_acc` came from its own FASTA table, and the ranking helper derives `cleaned_acc` in either case.
- The kernel repair above (the protein ids from the row names of `E`) is a limpa-version compatibility repair of a reproduced defect, not a scientific change: the quantities are unchanged and an engine returning `genes$protein.id` is unaffected.
- The accession kernel stores its arguments under the section the alias it is called through names (`chooseBestProteinAccessionFn`, as the DIA protein cleanup declaration already does); the record reads the step's parameters from the provenance values.
- No RLE/PCA/density/Pearson protein plots are published by the DPC step (the DIA route draws them at normalisation); KIT-041's normalisation tab is where they belong on this route.
- `document()` regenerated the three module Rd files, the limpa method's Rd and the NAMESPACE exports; unrelated roxygen drift it also produced (`runProteinIqRollupApplyStep`'s export, `runTestsContrasts.Rd`, a `ProteinQuantitativeData-class.Rd` line) was reverted to keep the change bounded; recorded here for a documentation ticket.
