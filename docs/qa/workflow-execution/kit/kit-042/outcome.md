# KIT-042: Legacy proteomics sessions adopted for every workflow type

Status 2026-10-20: **completed; implemented at `73b909e9`** (ticket revision 1.2); the control build's LFQ and TMT `filtered_session_data` sessions adopt into typed owners through the DA load handler, with and without an owner attached, hydrate identically, reproduce the control build's DA tables, export natively and reopen; the retired limpa route is refused by name. Tests, check and install below.

## What changed (one mechanism: session adoption)

- `ingestDIANativeLegacySession` (`R/utils_workflow_dia_sessions.R`) adopts every type the owner serves (`DIA`, `LFQ`, `TMT`; any other `workflow_type` still returns FALSE, as does a non-Linux host); a session carrying `use_limpa`, `limpa_applied` or `limpa_dpc_quant_results` aborts with `workflow_session_unsupported` ("sessions from the retired in-memory limpa route cannot be adopted; rerun on the DIA with limpa workflow") instead of returning FALSE. The store label is `DIA-IQ-native` for DIA (unchanged ids), otherwise the session's recorded `data_format` as KIT-020 labels it, or `<TYPE>-native` when the in-memory collector recorded no format (the control build's sessions carry none, so they adopt as `LFQ-native`/`TMT-native`). The head's `workflow_type` is the session's. Every adopted scientific state gets a `legacy` provenance entry written at ingest by the adopting build (not marked `backfilled`; the `initial` placeholder keeps the owner's `import` entry), so the KIT-025 reopen backfill finds nothing to add. The DIA-NN quantification method is set only for DIA. When the ingest replaces an existing owner, the bus's `data_tbl`/`data_cln` references into that owner are released before it closes (found by the with-owner check: the native export otherwise read a dangling reference; the legacy envelope carries no import table).
- `convertDIANativeLegacyCheckpoints` is class-generic already (verified: `ProteinQuantitativeData` states convert to `dia.component_checkpoint.v2`).
- `collectDIANativeSessionMetadata` no longer refuses by `use_limpa` (the limpa route becomes a workflow type, KIT-046; the in-memory limpa route never attaches an owner); `workflow_type` is the store identity's (KIT-020), with the config and the state record as fallbacks. `runProtNormExportSessionWorkflow` keeps its three branches unchanged; an LFQ/TMT owner takes the native branch.
- `da_server_load_session_handler` (`R/mod_prot_da_handlers_load_session.R`): **verified only**; it already takes the adopted owner from the ingest for every type and assigns `$states`/`$state_history` directly only on a plain `WorkflowState`. Not modified.

## Deviations and claim limits

- The limpa-route RDS is the MaxQuant session with the route's flags set, not a workbook run of the retired route on the control build (the refusal keys on exactly those flags, which the in-memory collector wrote for that route; a real run would add `limpa_dpc_quant_results`, also refused).
- The in-memory collector records no `data_format`, so adopted LFQ/TMT owners are labelled by type; under KIT-020's gate such an owner accepts no later import (reset the project first), where a `DIA-IQ-native` owner accepts a DIA-NN re-import.
- The `filtered_session_latest.json` pointer names the archive; the workflow type is in the archive's `manifest.json` (`workflow`) and in the session metadata (`workflow_type`), both checked.
