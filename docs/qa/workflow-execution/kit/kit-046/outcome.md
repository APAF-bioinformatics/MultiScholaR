# KIT-046: DIA_LIMPA as a workflow type: entry point, owner, step specs, template; the DIA route without limpa

Status 2026-10-21: **completed** (ticket revision 2.1). Implemented at `ee757cde` (documentation of the new UI argument at `a3722916`); install `kit_046` = `core/browser-smoke.2M9Eyi` (source `f63e0c59`); no counted member.

## One mechanism: a workflow type

- **Type value and owner.** `WorkflowState$setWorkflowType` and the owner's override accept `DIA_LIMPA`. `workflowTypeForImportFormat(format, data_type, dia_route)` maps a DIA-NN import to `DIA` or `DIA_LIMPA` by the route chosen at the entry point; `workflowRoutesByType` gains `DIA_LIMPA = "limpa"` (the native session manifest's route, through `workflowRouteForType`); `workflowNativeStoreLabel(format, type)` names the store `DIA-LIMPA-native`. `initializeDIANativeImport` sets the route type on the manager before the import on every platform and, on Linux, attaches the owner for `DIA_LIMPA` exactly as for `DIA`; it refuses with `workflow_engine_unavailable` ("DIA with limpa needs the limpa package; fastlimpadpc is the default engine when installed") when `limpa` is absent; an owner never changes route (`saved_entity_scope`). `describeDIAProteinState` and `collectDIANativeSessionMetadata` derive the limpa flag from the type (KIT-042 audit F-08 closed); `validateDIAPeptideCheckpointRoute` reads the archive's `workflow_type`; the peptide checkpoint archive no longer writes the retired method field; `adoptDIANativeSession`, `ingestDIANativeLegacySession` and `openDIAPeptideCheckpoint` no longer set it.
- **Entry point.** The `dia_quantification_method` radio is replaced by `dia_route` with "DIA, iq MaxLFQ (optional replicate-mean imputation)" (`DIA`) and "DIA with imputation leveraging limpa (Li et al. 2025)" (`DIA_LIMPA`); the import observers pass the route; `applyProtImportResultToWorkflow` keeps a DIA-NN manager's route type. `grep -rn "dia_quantification_method" R/` is empty.
- **Step lists by type.** `getProtQcPeptideModuleSpecs("DIA_LIMPA")`: `qvalue_filter`, `rollup`, `log2_matrix` and `accession_cleanup` (the last two KIT-047 placeholders, tabs saying "declared in KIT-047"); `getProtQcProteinModuleSpecs("DIA_LIMPA")`: `dpc_quant` (KIT-047), `normalisation`, `peptide_count` (KIT-041 placeholders); `mod_prot_qc_peptide_ui(id, workflowType)`; the QC render and routing and the design builder treat `DIA_LIMPA` as peptide-level like `DIA`.
- **The DIA route without limpa.** The rollup tab's method radio, `runProteinLimpaRollupApplyStep` and `buildProtTestModeLimpaProteinObject` are removed (`grep -rn "limpa" R/mod_prot_qc_protein_rollup.R` is empty); the report template follows the workflow type alone (`dia_limpa` → `DIANN_limpa_report.rmd`; a `DIA` project with a `[proteinMissingValueImputationLimpa]` section and limpa arguments selects `DIANN_report.rmd`); the normalisation export's `limpa_applied`/`use_limpa` follow the type and the export no longer reads `proteinMissingValueImputationLimpa` from the object's arguments (KIT-047 records the DPC parameters on the head). `grep -rn "proteinMissingValueImputationLimpa" R/utils_workflow_dia_state.R R/mod_prot_summary_report_helpers.R R/mod_prot_norm_session_helpers.R` is empty.
- **Record.** `buildWorkflowAnalysisRecord` writes `workflow` from the snapshot (generic); the replay's precondition check reads states, not types.

## Deviations and claim limits

- The `DIA_LIMPA` route computes nothing new: import, design, Q-value and rollup are the shared declarations; its later steps are placeholders until KIT-047 and KIT-041.
- `limpa` is installed in the user library, not the proof library; the route check ran where `requireNamespace("limpa")` is TRUE (recorded in the JSON); the native-session test covers both outcomes.
- The kit's journey driver never set the removed radio (its settings come from the bindings), so the DIA journey members are unaffected; the CORE-pinned `workflow_checkpoint_dia_driver.R` still names `rollup-rollup_method` in its own proof journey and is untouched (CORE builds carry the radio).
