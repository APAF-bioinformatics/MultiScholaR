## Deviations and claim limits

- **Step-map units and the replicate rule recorded without the user's confirmation row** (afk): `protein_normalisation_limpa` whole matrix, `peptide_count` row, `ruv_covariates` whole matrix; RUV-III's replicate structure follows KIT-035's rule (the technical block when declared, else the grouping variable; the script used `group`); `config$replicate_structure` names the rule applied. On the screen fixture (no technical replicates) the two coincide (`group`); on the small fixture the technical block applies.
- **Tab order**: the script runs the correlation filter before RUV, so on `DIA_LIMPA` the RUV covariates run after the correlation sub-step; the tab's normalisation button is a pass-through on this route (the between-sample normalisation is a protein QC step). The ticket's wording ("runs `protein_ruv_covariates` through the managed step" from the normalisation tab) is met by the in-process declaration run after the correlation step, the `normalization-ruv` pattern; a managed-worker variant of a whole-matrix in-process declaration is refused by KIT-024's rule.
- The `[ruvCovariates]` parameters are read from the project's configuration (shipped defaults when absent) and the tab's RUV grouping variable; the tab exposes no further inputs for them (bounded; the DIA tab's automatic-mode inputs are its own).
- The vendored script's result names two fields that are NULL in its return (`best_composite_score`, `best_cancor_plot`, a naming slip in the script); the package result carries them; the comparison is on percentage, k, controls, separation score and the trace.
- `assertDIAExportReady`'s list of QC-pending states does not name the route's new states; their pending publication is handled by `resumeDIAProteinAction` as for every protein step.
