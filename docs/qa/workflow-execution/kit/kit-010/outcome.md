## What was built

1. **`partitionByRows(scope, columns, kernel, consume, worker_cap, working_bytes_per_row, overhead_bytes, policy)`** in `R/utils_workflow_partitions.R`: pages of rows from the row streamer (`streamWorkflowTableRows`: 10,000 rows per page in source order; a wide table read in 64-column blocks), the kernel once per page with the page's source offset, `consume` per kernel value; the admission estimate is one page's working set from the declared working bytes per row plus the step's fixed overhead, refused above the cap and recorded. No scientific table, column or operation is named in the file (test).
2. **Wide-table sample projection** (audit B24). `readDIAExecutionComponents(manager, reference, fields, columns = list(<assay> = c(<key>, <samples>)))` projects a wide assay to selected sample columns through the class declaration; when the selection names sample columns, the design is hydrated and restricted to them whatever `fields` says, so the rebuilt object's sample sets agree (the class validity requires it); a selection of identifier columns alone keeps the design as `fields` requests it. The column caps: `materializeDIATable` and `streamWorkflowTableRows` already read any width in 64-column blocks, so a full or projected read of a 301-column table needs no new limit; `readSavedWorkflowTable`'s `max_columns = 64` stays the page API's cap, and the row partitioner writes wide pages through the parquet writer (no 64-column cap). Unit test on a 300-sample, 300-protein wide fixture: every column streams in one page; 150 of 300 samples project with the design following.
3. **The protein replicate filter as an operation on the row unit** (audit B23). `computeDIAReferenceProteinReplicateFilter(manager, reference, parameters, worker_cap, variant)`: `rows` (production) runs the unchanged `removeProteinsWithOnlyOneReplicate` kernel once per page of the wide table through `partitionByRows`, streams the retained rows to the bounded table writer under the input prototype's contract, recomputes the design once on the merged output (`cleanDesignMatrix`) and records the kernel's arguments as the GUI does (through the module's injectable alias, which the kernel records under as well); `whole` hydrates the object and runs the kernel once, as the GUI's in-process step does (the control arm). The registry entry `protein_replicate_filter` (input `checkpoint`, class `ProteinQuantitativeData`, parameters `grouping_variable`, `parallel_cores`; variants `whole`/`rows`, default `rows`; step label `13_protein_replicate_filtered`) carries the new `protein` compute, completion and publication roles: the completion commits the state and records the bounded display product as the GUI's `finishDIAProteinAction` does (now with a `publish` switch), and `publishWorkflowProteinResult` publishes the files and figures in the controller's publication phase through the existing protein output path. The GUI's protein module keeps its in-process path (KIT-015 declares the protein QC steps).
4. **Harness.** The verifier and the population input helper name the state's assay component through the class declaration (a peptide long table or a protein wide table). Generator: `tickets$010` once `kit_010` is bound.
