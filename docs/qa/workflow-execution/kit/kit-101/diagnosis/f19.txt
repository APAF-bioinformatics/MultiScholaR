VERDICT: MIXED. The main cause is a fixture artefact: an unnormalised, group-imbalanced sample loading shift. It hits
a route property: the DIA_LIMPA route does no between-sample normalisation by default, and in fact cannot, see 4.
RUV-III covariates (k = 1 or 2) and the qvalue() pi0 estimate then roughly double the false positives
(a statistical property at n = 8). limpa/DPC itself is not the cause.

   Reading:
   - Every unnormalised variant (a, b, c, c', d1, d2) shows a common logFC shift of about -0.26 to -0.31 on the
     null proteins and 43-106 null proteins at p < 0.05. Centring (f1, f4) or the DIA route's cyclicloess (e)
     removes the shift and brings false positives to 1-4 (BH 0-3).
   - limpa/DPC is not the cause: plain limma on the DPC matrix (d1) and a plain peptide mean (d2) show the same
     shift. Centred dpcDE (f1: 4 FP) is close to the centred plain mean (f4: 1 FP).
   - RUV covariates add false positives on top: 12 -> 21 (k=1) -> 23 (k=2) unnormalised; 4 -> 6 centred. W is
     uncorrelated with group (r = 0.008, 0.026). W1 is about -24.5 in every sample (the control proteins' level),
     so the factors carry little real unwanted variation on this synthetic data, and the eBayes fit loses df at n = 8.
   - The q column (qvalue() pi0 < 1) is more liberal than BH in every unnormalised variant (41 vs 23 for the GUI
     state). That doubles the visible false positives once the null p-values are inflated by the shift.
   - RUV-III correction mode (KIT-056; the matrix is replaced by newY with the DPC standard errors kept and no df
     correction) is much worse: 112 calls, 88 false positives. Not used by the lane, but a statistical hazard of the
     mode at small n (the k factors' degrees of freedom are not removed from the limma fit).

3. The fixture (f19_fixture.R; the generator reproduces report.tsv byte for byte, sha256 bcf39178...)
   - kitProteinMatrix (tools/profiling/kit_protein_corpus.R) adds a per-sample loading term sample_scale ~ N(0, 0.25).
     At seed 20261109 with 4 + 4 samples, the draws are WT -0.050, 0.418, 0.258, -0.003 and KO -0.129, -0.061,
     -0.302, -0.098. Mean KO - WT = -0.303 log2: a loading difference confounded with the group by chance.
   - generateProtDiannFixture writes Precursor.Normalised = Precursor.Quantity x run_scale (run_scale ~ 2^N(0, 0.1);
     KO - WT -0.016). Real DIA-NN Precursor.Normalised is DIA-NN's own cross-run normalisation, so a loading
     difference like this would be largely removed. The fixture's "normalised" column is not normalised.
     Per-run median log2 Precursor.Normalised: WT 20.25 20.48 20.39 20.14, KO 19.95 19.86 19.74 20.14. The DPC EList
     per-sample medians: KO - WT = -0.365.
   - Oracle analyses on the true protein matrix (limma, BH): unnormalised 27 sig / 17 planted / 10 FP (median null
     logFC -0.299); median-centred 19 / 19 / 0. The fixture alone produces about 10 false positives for any
     unnormalised analysis.
   - The other parts of the fixture are not the cause: peptides per protein 1:66, 2:130, 3:105, 4:99. Precursor
     missingness is similar by group (non-planted WT 11.8%, KO 12.6%; planted 13.5% / 14.5%). 274 of 3200
     protein-run cells have no precursor. Non-planted proteins get no group-correlated noise: residual N(0, 0.4)
     iid, precursor offsets fixed across runs.
   - The other lanes (prot_dia, TMT, LFQ) come from the same recipe with other seeds. They normalise (cyclicloess),
     so a chance loading imbalance there does not reach the DA.

4. A latent defect found on the way (f19_norm_check.R)
   On DIA_LIMPA, the protein QC "Between-Sample Normalisation" step (computeDIAReferenceProteinNormalisation ->
   normaliseBetweenSamples) changes only protein_quant_table. The DA's dpcDE branch (R/func_prot_da_model_methods.R
   ~367-392) fits args$limpa_dpc_quant_results$quantified_elist, whose E nothing updates. Measured on the pre-RUV
   state: cyclicloess changes the protein table (max abs diff 0.510), the EList E is unchanged (identical), and the
   DA calls are the same (27 / 15 / 12 both ways). So choosing a normalisation on this route has no effect on its DA.
   The route default (config.ini [limpaProteinNormalisation] method=none, "the limpa script's choice") hides this.
   (Not checked: which matrix the route's QC plots read. Anything that reads protein_quant_table would show a
   normalised matrix while the DA fits an unnormalised one.)

5. Conclusion and smallest fix candidates (not implemented)
   - Cause: mixed. (i) A fixture artefact: the DIA-NN fixture's Precursor.Normalised carries a -0.30 log2
     group-confounded loading difference that real DIA-NN normalisation would remove. (ii) A genuine route property:
     DIA_LIMPA does no between-sample normalisation (default none), and a chosen one cannot reach dpcDE (defect,
     section 4). (iii) A statistical property: RUV-III covariates at n = 8 with 20 controls and qvalue()'s pi0 add
     false positives once the null is shifted.
   - Fixture candidate (changes only the prot_dia_limpa lane): write Precursor.Normalised with the per-run loading
     removed (for example Precursor.Quantity / 2^(sample_scale + run log-shift), DIA-NN-like). Measured proxy: f1/f2
     (centred) give 4-6 FP and 15-16 planted (BH 3-5). Limit the change to the DIA_LIMPA lane or both DIA-NN lanes.
     Changing the shared generator for both changes prot_dia's fixture and its oracle too (the user decides the scope).
     Re-freeze prot_dia_limpa (and prot_dia if included).
   - Code candidate for the section 4 defect (smallest): when normaliseBetweenSamples runs on an object that carries
     limpa_dpc_quant_results$quantified_elist, apply the same per-sample normalisation to E (or have the limpa
     normalisation step write the normalised matrix into E, as the RUV correction mode already does with newY). With
     the default "none" it changes no current output or oracle. Whether the route's default should become a
     normalisation (for example median or cyclicloess on E) is a separate scientific decision for the user. That
     would change the prot_dia_limpa lane and every DIA_LIMPA journey oracle recorded with method none (KIT-041 to
     KIT-065).
   - RUV correction mode false positives (c'): record as a statistical caveat or ticket. No fix proposed here.
   Confidence: high (GUI result reproduced exactly; each factor isolated by one change at a time; ground truth from
   the generator).
