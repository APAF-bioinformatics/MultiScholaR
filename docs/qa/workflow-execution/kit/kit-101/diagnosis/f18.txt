VERDICT: CONFIRMED. Neither reader, nor anything after it on the LFQ route, turns a 0 into NA. The design step
applies log2(x + 1), so a 0 becomes a log2 value of 0 (about 20 log2 units below the data). Normalisation then moves
it to large negative values. The correlation filter and the DA see it as a real measurement.

2. What 0 means in these columns (the semantics this relies on)
   - MaxQuant proteinGroups.txt "LFQ intensity <exp>" / "Intensity <exp>": MaxQuant writes 0 when the protein group
     was not quantified in that experiment. The usual downstream practice treats 0 as missing (Perseus: log transform,
     then 0 -> NaN; the MaxLFQ/DEP-style R importers convert 0 to NA). This is well established in the field, but I
     did not re-verify it against MaxQuant's own documentation in this session (I found no page that states it).
   - FragPipe combined_protein.tsv "<sample> MaxLFQ Intensity" / "<sample> Intensity" (IonQuant): 0 when the
     protein was not quantified in that sample. External evidence found this session: the autonomics Bioconductor
     package's FragPipe reader applies zero_to_na() to the MaxLFQ and Intensity assays before log2
     (https://rdrr.io/github/bhagwataditya/autonomics/src/R/3.4_read_fragpipe.R). FragPipe's own docs pages I could
     reach (tutorial_perseus, FragPipe-Analyst) do not state the rule explicitly. Confidence: high that 0 means "not
     quantified" for MaxLFQ (a MaxLFQ ratio-derived intensity is never truly 0), and medium on the citation.
   - A true intensity of exactly 0 is not a measurement either tool reports for a quantified protein.

3. Parity with the other omics and routes
   - DIA (DIA-NN): a missing precursor has no row, so it is absent rather than 0. On DIA_LIMPA, the log2 peptide
     matrix maps values <= 0 to NA (log2TransformPeptideMatrix, R/func_pept_s4_norm_methods.R:115; declaration fixed
     `nonpositive_to_na = TRUE`). The DIA (IQ) route's handling of a literal 0 in Precursor.Normalised was not traced
     in this diagnosis (iq's preprocessing applies a log2 intensity cutoff, I believe, but that is unverified here).
   - TMT (Proteome Discoverer): PD leaves a missing abundance empty, so it reads as NA. A literal 0 would take the
     same design step log2(x + 1) as LFQ and be kept (no 0 -> NA in importProteomeDiscovererTMTData). This is the
     same latent behaviour, but PD does not normally write 0.
   - Lipidomics and metabolomics: logTransformAssays uses log2(x + offset), offset 1 by default
     (R/func_lipid_s4_normalization_methods.R:586, R/func_metab_s4_transformation_methods.R:117). Its documentation
     says "Zeros in the data are handled by adding a small offset", so zeros are kept as quantities by design. Only
     some QC summaries exclude Intensity > 0 (CV, counts). No import converts 0 -> NA. That is the same behaviour as
     the LFQ route, and whether it is right for MS-DIAL/LipidSearch zeros is a separate question. It is not part of
     F-18.
   So the LFQ route matches lipid/metab (zeros kept) and differs from DIA/DIA_LIMPA (zeros or absences are missing).

5. Scientific impact and smallest fix candidate (not implemented)
   Impact: every MaxQuant/FragPipe LFQ analysis with any not-quantified cell carries 0 values about 20 log2 units
   below the data. Cyclicloess pulls them to between -5 and -15. They dominate the Pearson correlations, so samples
   are removed for the wrong reason, and they inflate variance or fake fold changes in limma. At 8% zeros on the
   synthetic fixture, the LFQ DA collapses (MaxQuant: 3 calls, 1 true) or cannot run (FragPipe). Real LFQ exports
   (KIT-054: about 52% missing) are affected more.
   Smallest fix candidate: convert 0 to NA at the two readers, where the tool semantics are known. One change in
   each pivot, for example `Intensity = dplyr::na_if(as.numeric(Intensity), 0)`, in importMaxQuantData and in
   importFragPipeData. The design step's log2(x + 1) stays as it is (it then never sees a 0). Alternative (broader,
   not recommended as the smallest): treat 0 as NA in buildProtDesignStateCheckpoint for TMT and LFQ. That would also
   cover a PD 0.
   What it would change:
   - Tests: tests/testthat/test-module-ci-prot-import.R MCI-004.3 pins the current behaviour
     (`expect_true(any(imported$data$Intensity == 0))`, from module_ci_prot_make_maxquant's 0 cell) and would need
     its expectation inverted. Reader tests in test-prot-import-maxquant-direct-shared.R, test-prot-01-import.R and
     test-workflow-native-session.R use no zeros in the cells they assert (check when fixing).
   - Oracles: KIT-021 lfq_300 populations and DA tables (lfq_300_*; 8% zeros). KIT-054 kc_lfq oracles (real data,
     zeros likely). These are historical records of completed tickets: re-recording versus annotating them is a
     user decision.
   - Unchanged: the entry-suite lanes prot_lfq and prot_lfq_fragpipe (fixtures have no zeros, so the oracles do not
     change); lfq_fixture / lfq48 / lfq65 journeys; prot_tmt (PD empties); the DIA lanes. After a fix, the LFQ lane
     fixtures could carry the recipe's 8% missing again (fixture/oracle change, the user's choice).
   Confidence: high on the mechanism and its effect on this synthetic data (traced through the production states).
   Medium on the external semantics citation.
