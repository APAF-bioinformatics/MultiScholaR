# Plan: KIT-031 (the planning gate) — lipidomics declarations, the kit's completeness test

## Context

Stage 3 of the KIT series has put the lipidomics module on the kit's foundations: the route and corpus (KIT-068), the bus (KIT-030), the carry-over repairs (KIT-069), the on-disk owner (KIT-070) and owned sessions (KIT-071, closed 2026-10-31 at 843ff460, kit_071 = `browser-smoke.U3g1Dl`). Every lipid commit is a reference commit of `LipidomicsAssayData`, but its provenance reads `legacy` because no lipid site names an operation: the analysis record lists every step incomplete, the replay refuses the first step, and the kit judges the lipid member `in_memory` (no oracles bound), never `exact`.

KIT-031 expresses every lipidomics step as a registered declaration with complete provenance, builds the record, replays it, and measures one screen lifecycle member exact against an in-process record through the report. It is the acceptance test of the kit's own rule (README "Rules the kit keeps"): *a new workflow writes one class declaration, one declaration per step, its kernels and its modules on the request/poll pattern; nothing else*. The ticket's rule: declarations, registry entries, record branches and module request/poll code only; a kit **function** gap stops the ticket and returns as an addendum. This plan is the ticket's `needs_planning` gate; it authors the full ticket (files, items, tests, exit) from the exploration below.

User decisions already taken: `ceiling()` removed from the lipid intensity-filter threshold in this ticket before any oracle is recorded (2026-10-28); the DA output is the manifest `lipid.da_results.v1`, not the S4 result class (2026-10-29); the three step-map flags answered as read (2026-10-29: intensity = row after the per-assay quantile pre-pass, ITSD = complete_sample with the mean-factor pre-pass, correlation = whole_matrix); lifecycle members only, no counted member; **full report overlay now** (this planning, 2026-10-31: sources table, bundle export from the lipid summary tab, and the record-reading chunk in `lipidomics_report.rmd`).

## What the exploration established (binding for the ticket text)

**The proteomics pattern the lipid steps mirror** (`R/utils_workflow_operations.R`): a declaration is `newWorkflowOperation(name, input_class, fields, unit, kernel(object, parameters, store), output_class, parameters, product_type, global_statistics, merge, fixed)` (:30); `unit`/`global_statistics`/`merge` are descriptive and validated (`merge` required for row/complete_sample/feature_group, forbidden for whole_matrix/store; :99-103). `omic_type`, compute/completion/publication roles, `step_label`, variants live on the **registry entry** (`validateWorkflowOperationEntry` :215-243; `registerBuiltinWorkflowOperations` :422-580, all 25 entries `omic_type = "proteomics"`). The in-process entries are registered by one loop (:570-578, `compute = completion = publication = "in_process"`, `handler = NULL`, variants `"whole"`) and run through `runSavedOperation(manager, declaration, source, parameters)` (:124-155), which sets the pending provenance (`setWorkflowStepProvenance`, :136), computes the identity, runs `runProjected` (hydrates `fields`, calls the kernel; :162) and saves/roots the product; the caller commits the state (`commitWorkflowReferenceState`) — the GUI pattern is `runDIAReferenceNormalization` (`R/utils_workflow_dia_products.R:501-560`). The worker request/poll chain (`installWorkflowManagedStep` → `beginWorkflowGUIAction` → `runWorkflowAction` → `pollWorkflowAction`) is bound to the proteomics compute roles (`computeWorkflowPeptideAction` accepts peptide/protein only; the enums are pinned by `test-workflow-operation-registry.R:76`). **Decision: every lipid declaration is in-process** (the review's "partitioned units run projected, the `whole` variant"); worker roles for lipidomics would be new infrastructure, i.e. a kit gap, and nothing in stage 3 needs them (no memory claim).

**Provenance.** `takeDIAStepProvenance` yields `legacy` when nothing is pending (`R/utils_workflow_dia_state.R:774`); `runSavedOperation` sets it; the proteomics design step sets `"design_builder"` (`R/mod_prot_design_state_helpers.R:15`); inputs are recorded with `recordDIAWorkflowInputs` (`:2444`). A record step is complete when its operation is registered, its declared parameters resolve from `args[[section]]`/provenance `values`/state `config` (`workflowRecordDeclaredParameters`, `R/utils_workflow_analysis_record.R:84-94`) and inputs exist. The section map `workflowSectionOperationsByType` (keyed by workflow type, `R/utils_workflow_operations.R:55-59`) reverses into the record's args lookup (:174); operation ids are global.

**Record and replay** (`R/utils_workflow_analysis_record.R`): `buildWorkflowAnalysisRecord` carries `omic_type` (KIT-070); `analyses$differential_abundance` (:270-287) hard-codes `DA-contrast-output` and `da_proteins_long`; `workflowRecordStepOutcomes` (:118) has a branch for `normalization-ruv` only. `replayWorkflowAnalysisRecord` (:421-566) accepts input roles `lipid_assay`/`design_file` (KIT-070), treats leading `import`/`design_builder` steps as preconditions, has hand-written per-operation branches (peptide/protein compute, `normalization-ruv`, `pearson-selection`, `protein_ruv_covariates`) and aborts `workflow_replay_unsupported` for anything else (:542); the DA re-run calls `runDIAReferenceDaAnalysis` (:561). Report overlay: `workflowRecordReportSources` (:684) keyed by report variable → `c(<operation>, <param>)`/software/outcomes/model; `workflowRecordReportParameters` (:751) called only from the four proteomics templates; `exportWorkflowAnalysisRecordBundle` (:671) wired only from `R/mod_prot_summary_report_helpers.R:510`. `workflowOperationDefaults` (:251) and `workflowParameterLabels` (:327) must cover every declared parameter (registry tests :236-257).

**The DA manifest pattern** (`dia.da_results.v1`): declared in `workflowOutputDeclarations` (`R/utils_workflow_class_declarations.R:70-77`, `identifies = "isDIAResultManifest"`), produced by `runDIAReferenceDaAnalysis` (`R/utils_workflow_dia_da.R:335-427`: manifest built, the DA arguments committed on the head, `runSavedOperation(diaContrastOperation())` per contrast, `clearDIAStepProvenance`, saved with `saveDIAStateValue(context, manifest, "da-result-references")`, `snapshot$da_results`). `LipidomicsDifferentialAbundanceResults` is declared (:43-45) but the GUI never builds it.

## The cut: two bounded items in one ticket (the KIT-070 shape)

## Kit-gap watch (stop-and-addendum triggers)

- `runProjected`/`readWorkflowExecutionComponents` cannot hydrate a `lists` assay with scalar slots the kernels read (`internal_standard_regex`, `lipid_id_column`, `@args`) → a kit function gap.
- `runSavedOperation`'s identity/cache or `store$table`/`store$product` cannot hold a per-assay list of tables → gap.
- `kitReproduceMismatches` cannot compare a `lists` assay component or the DA manifest's per-assay tables → gap.
- Anything else that needs an enum, a new role or a harness function rather than an entry, a declaration, a record branch or module code.
