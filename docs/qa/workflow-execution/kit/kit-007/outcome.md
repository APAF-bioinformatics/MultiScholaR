## What was built

- **Registry** (`R/utils_workflow_operations.R`): `registerWorkflowOperation(entry)`, `workflowOperationEntry(name)`, `workflowOperationNames()`, `workflowGuiQualifiedOperation()`, `registerBuiltinWorkflowOperations()`; a process-level environment filled at namespace load (`.onLoad`, `R/zzz.R`) and on first use. An entry carries every per-operation fact the execution layer named by hand: input role and class, parameter validator, resolver and byte limit, compute handler, completion and publication roles, step label, allowed adapters and GUI qualification variants, omic type, the diagnostic-only flag and (for the scientific operations) the KIT-006 declaration. Entries hold handler *names*, never closures: handlers never travel in requests, and the execution layer resolves a name in its own environment at the call site (so the audit tests that source the execution file and mock by name still hold).
- **Built-ins**: `wfx_fixture` (diagnostic only), `precursor_rollup` (from `diaPrecursorRollupOperation()`, variant `p14`, label `4_precursor_rollup`), `minimum_peptides_per_sample` (from `diaSampleFilterOperation()`, variants `native`/`physical`/`selection`, GUI variants `native`/`physical`, label `6_sample_filtered`, byte limit 262,144, resolver, inclusion-absence completion argument).
- **Execution layer by registry** (`R/utils_workflow_execution.R`): `workflowActionSpec` is the registry lookup; `validateWorkflowActionParameters` reads the byte limit and dispatches the entry's validator (`validateWorkflowPrecursorRollupParameters`, `validateWorkflowSampleFilterParameters`, `validateWorkflowFixtureParameters`); `computeWorkflowPeptideAction` dispatches the entry's handler (`computeWorkflowPrecursorRollupAction`, `computeWorkflowSampleFilterAction`); `resolveWorkflowActionParameters` dispatches the entry's resolver (`resolveWorkflowSampleFilterParameters`); `workflowQualificationVariant` reads the entry's variants and GUI variants; `publishWorkflowPeptideResult` reads the step label and omic type; `beginWorkflowGUIAction` checks the publication's omic type against the entry; `validateWorkflowActionInput` checks the record class against the entry's input class; `completeWorkflowAction` reads the completion role and the inclusion-absence flag; `prepareWorkflowHeadAcceptance`, the fixture compute guard, the fixture result, `finishWorkflowExecutionJob`'s spill fields and the fixture runner read `workflowFixtureOperation` or the diagnostic-only flag; `launchWorkflowApplication` resolves the GUI-qualified operation from the registry. Refusal classes unchanged (`workflow_execution_unsupported` for unregistered names and undeclared input classes, `workflow_execution_invalid` for parameters and variants).
- **Vehicle**: `test-workflow-execution-adapters.R` takes the operation list from the installed build's registry, falling back to the two frozen names on a build without one (the controls before KIT-007).
- **Harness**: the operation lifecycle pair runs on `operation_lifecycle$build` when bound (`kit_007`), else on the control.

Grep evidence (acceptance 1): after the change the only operation literal in `R/utils_workflow_execution.R` is the constant `workflowFixtureOperation`; every former site (`prepareWorkflowHeadAcceptance`, `beginWorkflowGUIAction`, `launchWorkflowApplication`, `computeWorkflowFixture`, `workflowWorkerMain`, `publishWorkflowFixtureResult`, `finishWorkflowExecutionJob`, the fixture runner, `validateWorkflowActionParameters`, `computeWorkflowPeptideAction`, `workflowQualificationVariant` (both programmes), `publishWorkflowPeptideResult` (label, omic type, directories), `workflowActionSpec`, `validateWorkflowActionInput`, `resolveWorkflowActionParameters`, `completeWorkflowAction`) reads the registry entry.
