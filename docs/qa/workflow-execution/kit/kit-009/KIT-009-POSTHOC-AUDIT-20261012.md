So: the mechanism this ticket changed (where and how the kernel runs per batch) governs a phase that was already flat and cheap, because the per-group loop it replaced already delivered the same 10,000-row batches; the partitioner's admission can only refuse a batch above the cap, never shrink one below the codec's delivery bound. The two things that set the peak, the three-process floor (the CORE-018 finding) and the single-pass ordered output write, are shared by both arms and untouched by this ticket. The 0.952 anonymous ratio is below the loop's bookkeeping and the host's noise (KIT-005's two controls differed by 0.971) and was rightly not claimed.
